# 第2页 · 大型工程 Kotlin 规范与演进（Tech Lead）

## 一、模块间 API：空安全与默认参数策略

### 问题

多团队多模块下，如何规定 Kotlin API 的空安全与默认参数，避免互踩？

### 机制级答案

- **空安全契约即 API**：
  - 公共 API 显式 `T` / `T?`，禁止依赖平台类型穿越模块边界；
  - Kotlin 模块间类型已带空性；**暴露给 Java 模块**必须 `@Nullable`/`@NotNull`（androidx 或 JSR-305，全仓统一一种）；
  - 边界 DTO 校验：跨进程/网络反序列化对象在 API 门面收敛。
- **默认参数策略**：
  - 应用内模块：允许，但**公开 API 慎重**——默认值变更可能影响调用方源码兼容（新必选参数插入是破坏性）；
  - 库/跨团队 SDK：优先 `@JvmOverloads` 或显式重载/Builder，减少"隐式重载"；参数超过阈值（如 4+）用 options data class（可演进）；
  - 默认值应稳定、无环境依赖——默认值里读全局状态是隐形耦合。
- **@Throws / 异常声明**：跨 Java 边界受检异常策略统一（Kotlin 不强制）。
- **命名与可见性**：`internal` 不当安全边界（对 Java 是 public）；跨团队用模块边界 + API dump 审查。

### 【为什么这样设计】

空性与参数默认是**调用方可见行为**——统一注解与策略把"编译器方言"变成团队协议；options 对象为演进留缝，避免重载爆炸。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：平台类型禁令、默认值变更风险、internal 误用。
- 加分：API 检查清单 + CI 校验；分层（内部灵活/对外冻结）。
- 减分：各模块注解混用；公开 API 随意加带默认值的参数。

### 【追问链】

1. 如何强制？→ lint/detekt 规则 + binary-compatibility-validator；
2. Java 旧模块？→ 适配层注解收敛；
3. data class 作 options？→ 注意 equals 范围与 copy 浅拷贝（Language/1）。

## 二、二进制兼容与 API 演进

### 问题

如何在不炸下游的情况下演进 Kotlin 模块 API？

### 机制级答案

- **破坏性类型（源码/二进制）**：
  - 删除/重命名公开函数、类可见性收紧；
  - 泛型签名变更、参数类型变更；
  - 默认参数/默认值变更对 Kotlin 调用点合成 `$default` 的影响；
  - 改 companion/object 方法签名影响 Java `Companion` 调用面；
  - data class 主构造字段增删影响 equals/copy/组件方法。
- **相对安全**：新增函数/类、新增可选参数（Java 侧需重载已提供）、内部实现、`@Deprecated` 引导迁移。
- **工具化**：`binary-compatibility-validator`（apiDump/apiCheck）锁定公开声明快照进 CI；语义化版本 + changelog；大版本才做破坏。
- **弃用路径**：`@Deprecated(message, replaceWith, level)` → 至少一个版本周期 → 删除；Android 生态还有 min SDK 与 lint 替换建议配合。
- **模块拆分**：api 与 implementation 分离（Gradle），实现类不进 ABI；避免 export 传递依赖污染。

### 【为什么这样设计】

Kotlin 公共 API 的"编译产物契约"对下游生效——二进制兼容是组织间信任的工程化；弃用梯子给调用方迁移时间，避免"周末升级全红"。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：常见破坏清单、apiCheck、弃用节奏。
- 加分：多团队 monorepo 的 CODEOWNERS + api 评审；版本对齐火车。
- 减分：说"源码能编过就兼容"；无弃用直接删。

### 【追问链】

1. 只加默认参数一定安全？→ Kotlin 调用点源码多兼容；二进制看合成函数与旧调用——仍建议验证 api dump。
2. sealed/枚举新增分支？→ 见 Language/1：对 when 穷尽是源码破坏。
3. R8 后兼容？→ 兼容指开发态 ABI；运行时还有反射 keep 问题。

## 三、编译速度治理

### 问题

Kotlin 工程变大编译变慢，如何治理？

### 机制级答案

- **增量编译**：模块内变更只重编受影响文件——保护增量命中率：**减少"牵一发而动全身"的公共头文件/核心接口变更频率**，稳定 API 面。
- **模块拆分**：
  - 过大模块 → 拆 feature/core/api，缩短重编范围；
  - 反向陷阱：过度拆分增加配置与链接开销——按变更频率聚类（常变 UI 与稳核心分开）；
  - 依赖方向单向，避免环（环会破坏增量）。
- **并行与构建缓存**：Gradle 并行、configuration cache、远程构建缓存（以所用 Gradle/KGP 版本支持为准）；Kotlin daemon 内存合理配置。
- **语言特性成本**：
  - 大量 inline/内联多态与复杂泛型增加编译期类型检查压力——热库慎滥用巨型 inline；
  - KSP/注解处理与序列化插件的增量配置；
  - 避免在 api 模块放置无谓的巨型 sealed 层级强制全下游重编（变更敏感）。
- **流程**：编译时间监控（构建扫描/CI 曲线）、PR 级预算；IDE 与 CI 编译选项一致化。

### 【为什么这样设计】

编译速度是"依赖图 × 重编范围 × 单文件成本"三因子问题——模块边界与 API 稳定度决定图的形状，特性选择影响单点成本；治理靠架构决策而非只调 JVM 参数。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：增量命中、依赖环、拆分权衡、监控。
- 加分：给出"新模块准入"标准（大小、依赖数、变更频率）；与二进制兼容治理联动。
- 减分：一上来无限拆模块；只说开 daemon 不谈架构。

### 【追问链】

1. 何时拆？→ 编译/重编数据 + 团队 ownership；
2. 与 KMP？→ sourceSet 增加配置成本，需纳入预算；
3. 快速止血？→ 稳定核心 API、开构建缓存、清理无用依赖图边。

## 四、收束：tech lead 的 Kotlin 治理清单（速查）

- 空安全：边界注解统一、平台类型不穿透、反序列化校验；
- API：apiCheck 进 CI、弃用梯子、默认参数与 options 策略；
- 并发：作用域归属评审、禁 GlobalScope、异常与测试模板；
- 构建：模块按变更频率拆分、防依赖环、编译时间预算；
- 演进：试点→规范→工具强制，用数据反对流行度。
