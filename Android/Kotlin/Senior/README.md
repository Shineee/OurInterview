# Kotlin 专家收束（Senior / Tech Lead 向）

## 一、KMP 面试答法：expect / actual 与共享边界

### 问题

Kotlin Multiplatform 的核心机制是什么？共享层应该放什么、不该放什么？

### 机制级答案

- **核心**：一套 Kotlin 公共代码 + 各平台 sourceSet；`expect` 声明平台能力接口/函数，`actual` 在 Android/iOS/JVM/JS 等提供实现——**多平台不是"一份 UI 到处跑"**，默认共享的是业务/数据/域逻辑。
- **sourceSet 结构（概念级）**：commonMain 与 androidMain/iosMain 等；依赖与期望/实现按 sourceSet 图配置；以所用 Gradle/KMP 插件版本文档为准（API 面演进快）。
- **共享边界原则**：
  - **放**：纯 Kotlin 业务规则、状态机、协议解析、Repository 接口与可测试域模型、协程/Flow 组织的数据层；
  - **不放**：Activity/Fragment/Compose 专属 UI（UI 可 Compose Multiplatform 另议，生产决策要单独评估）、平台推送/权限/文件系统——用 expect/actual 或平台接口注入；
  - **桥**：依赖注入接口在 common，实现在平台模块——避免 common 反向依赖 AndroidX。
- **与 Android 生态**：现有 Android 模块可渐进抽 common；AndroidX/KMP 库（如 ktor、kotlinx-datetime、SQLDelight 类思路）补足跨平台能力；iOS 集成有 framework 导出与 Objective-C 互操作成本。
- **面试话术结构**：先问目标（降本/一致性/技术债）→ 划共享边界 → 说 expect/actual 与 DI → 说测试（commonTest）→ 说风险（构建复杂度、iOS 协作、人才）。

### 【为什么这样设计】

expect/actual 把平台差异收敛到**编译期可检查的声明点**，避免到处 `if (platform)`；共享逻辑最大化复用与一致性，平台差异显式化——复用的是"不变量"，不是"像素"。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：共享边界、expect 不是万能、构建与测试。
- 加分：渐进迁移路径（先数据/域）；提到 ABI/发布节奏与多平台测试矩阵成本；对比 RN/Flutter 的"共享 UI"路线差异（概念级）。
- 减分：宣称 KMP 一定省一半人力；把 UI 全塞 common 说"都能跑"。

### 【追问链】

1. expect 与接口抽象差异？→ 接口 + 平台 DI 更利于测试；expect 适合编译期绑定的小表面。
2. 如何测？→ commonTest 跑多平台任务；仪器测试仍平台。
3. 与 Compose Multiplatform 关系？→ UI 层可选共享，决策独立于数据层 KMP。

## 二、协程统一模型：服务端与 Android 一句话深度

### 问题

协程在 Android 与服务端（Ktor/Spring 等）是否同一模型？如何向团队解释统一性？

### 机制级答案

- **同一运行时核心**：CPS/状态机、CoroutineContext、Dispatcher、结构化并发、Flow——**平台无关**（kotlinx-coroutines）；Android 的 viewModelScope 与服务端的请求作用域只是**宿主生命周期不同**。
- **Dispatcher 差异**：Android 主线程 Main + IO/Default 池；服务端常是 Netty/Ktor 的事件循环或虚拟线程宿主——**模型统一，池策略按宿主调**。
- **Flow 统一**：服务端推送/流式响应与 Android 状态流同一组合子——团队共享操作符心智与测试工具（虚拟时间）。
- **互操作层**：Ktor 协程挂起 API ↔ Android 客户端协程——端到端"挂起到底"，减少回调适配层；注意取消与超时要端到端贯通（HTTP cancel 传播）。
- **叙事一句话**：协程是 Kotlin 的**结构化并发运行时**，生命周期由宿主（UI/请求/任务）注入 Context，业务代码不绑 Android API——这正是 KMP 共享数据层的前提。

### 【为什么这样设计】

语言级并发原语跨端一致，比"Android 独有 AsyncTask"类 API 有更长的技术半衰期——学习成本一次付清，宿主差异用 Dispatcher/Scope 适配。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：同一核心、宿主 scope、取消贯通。
- 加分：提到服务端背压/超时与 Flow/Channel 对应；团队培训路径。
- 减分：说"协程是 Android 特性"；忽视服务端线程模型差异只背名词。

### 【追问链】

1. 和虚拟线程关系？→ 可互补：JVM 虚拟线程解决阻塞生态，Kotlin 协程解决结构化逻辑并发（见 `../Java/Senior/JVMEngineering` 对照）。
2. 多平台测试？→ TestDispatcher 通用。
3. 监控？→ 跨端 tracing 与协程未完成任务观测（工程自建）。

## 三、何时不该用协程（性能与可维护性权衡）

### 问题

协程不是银弹。哪些场景应慎用或不用？

### 机制级答案

- **极高频微任务**：每秒百万级微小任务且延迟敏感——状态机分配与调度开销可能不如手写环形缓冲/无锁结构；先测量。
- **简单后台一句 IO**：脚本/工具线程可 `Thread`/`Executor` 更直接；引入 scope/取消样板收益低。
- **必须阻塞的遗留库**：无法中断的 native/同步调用——包在专用 Dispatcher + 超时，不要在 Main/Default 直接调；有时线程池隔离更可控。
- **复杂响应式已有栈**：存量 Rx 大型图不必强迁——混用经边界适配；迁移成本 > 收益要数据说话。
- **可维护性反模式**：滥用 GlobalScope、层层 launch 无归属、异常靠 catch 吞——**不用结构化并发的协程比线程更危险**（泄漏更隐蔽）。
- **硬实时**：Kotlin 协程不承诺硬实时截止；GC 与调度不确定——工业控制等另选技术栈。

### 【为什么这样设计】

抽象都有常数：状态机/调度/取消协议在不适合的负载下变成纯开销；工程选型 = 测量 + 团队掌握度 + 生态，不是流行度。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：有边界的技术观、测量意识、阻塞遗留封装。
- 加分：给出"引入协程的评审清单"（作用域归属/异常/测试/Dispatcher）。
- 减分：全面拥抱无治理；或全盘否定只用线程池。

### 【追问链】

1. 如何定评审清单？→ 作用域生命周期、异常路径、Dispatcher、可测性、取消是否贯通。
2. 性能基线？→ 微基准防 JIT 假象 + 场景压测。
3. 团队不熟？→ 先数据层试点 + 规范（Senior/2 页）。

## 一、模块间 API：空安全与默认参数策略

### 问题

多团队多模块下，如何规定 Kotlin API 的空安全与默认参数，避免互踩？

### 机制级答案

- **空安全契约即 API**：
  - 公共 API 显式 `T` / `T?`，禁止依赖平台类型穿越模块边界；
  - Kotlin 模块间类型已带空性；**暴露给 Java 模块**必须 `@Nullable`/`@NotNull`（androidx 或 JSR-305，全仓统一一种）；
  - 边界 DTO 校验：跨进程/网络反序列化对象在 API 门面收敛。
- **默认参数策略**：
  - 应用内模块：允许，但**公开 API 慎重**——默认值变更可能影响调用方源码兼容（新必选参数插入是破坏性）；
  - 库/跨团队 SDK：优先 `@JvmOverloads` 或显式重载/Builder，减少"隐式重载"；参数超过阈值（如 4+）用 options data class（可演进）；
  - 默认值应稳定、无环境依赖——默认值里读全局状态是隐形耦合。
- **@Throws / 异常声明**：跨 Java 边界受检异常策略统一（Kotlin 不强制）。
- **命名与可见性**：`internal` 不当安全边界（对 Java 是 public）；跨团队用模块边界 + API dump 审查。

### 【为什么这样设计】

空性与参数默认是**调用方可见行为**——统一注解与策略把"编译器方言"变成团队协议；options 对象为演进留缝，避免重载爆炸。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：平台类型禁令、默认值变更风险、internal 误用。
- 加分：API 检查清单 + CI 校验；分层（内部灵活/对外冻结）。
- 减分：各模块注解混用；公开 API 随意加带默认值的参数。

### 【追问链】

1. 如何强制？→ lint/detekt 规则 + binary-compatibility-validator；
2. Java 旧模块？→ 适配层注解收敛；
3. data class 作 options？→ 注意 equals 范围与 copy 浅拷贝（Language/1）。

## 二、二进制兼容与 API 演进

### 问题

如何在不炸下游的情况下演进 Kotlin 模块 API？

### 机制级答案

- **破坏性类型（源码/二进制）**：
  - 删除/重命名公开函数、类可见性收紧；
  - 泛型签名变更、参数类型变更；
  - 默认参数/默认值变更对 Kotlin 调用点合成 `$default` 的影响；
  - 改 companion/object 方法签名影响 Java `Companion` 调用面；
  - data class 主构造字段增删影响 equals/copy/组件方法。
- **相对安全**：新增函数/类、新增可选参数（Java 侧需重载已提供）、内部实现、`@Deprecated` 引导迁移。
- **工具化**：`binary-compatibility-validator`（apiDump/apiCheck）锁定公开声明快照进 CI；语义化版本 + changelog；大版本才做破坏。
- **弃用路径**：`@Deprecated(message, replaceWith, level)` → 至少一个版本周期 → 删除；Android 生态还有 min SDK 与 lint 替换建议配合。
- **模块拆分**：api 与 implementation 分离（Gradle），实现类不进 ABI；避免 export 传递依赖污染。

### 【为什么这样设计】

Kotlin 公共 API 的"编译产物契约"对下游生效——二进制兼容是组织间信任的工程化；弃用梯子给调用方迁移时间，避免"周末升级全红"。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：常见破坏清单、apiCheck、弃用节奏。
- 加分：多团队 monorepo 的 CODEOWNERS + api 评审；版本对齐火车。
- 减分：说"源码能编过就兼容"；无弃用直接删。

### 【追问链】

1. 只加默认参数一定安全？→ Kotlin 调用点源码多兼容；二进制看合成函数与旧调用——仍建议验证 api dump。
2. sealed/枚举新增分支？→ 见 Language/1：对 when 穷尽是源码破坏。
3. R8 后兼容？→ 兼容指开发态 ABI；运行时还有反射 keep 问题。

## 三、编译速度治理

### 问题

Kotlin 工程变大编译变慢，如何治理？

### 机制级答案

- **增量编译**：模块内变更只重编受影响文件——保护增量命中率：**减少"牵一发而动全身"的公共头文件/核心接口变更频率**，稳定 API 面。
- **模块拆分**：
  - 过大模块 → 拆 feature/core/api，缩短重编范围；
  - 反向陷阱：过度拆分增加配置与链接开销——按变更频率聚类（常变 UI 与稳核心分开）；
  - 依赖方向单向，避免环（环会破坏增量）。
- **并行与构建缓存**：Gradle 并行、configuration cache、远程构建缓存（以所用 Gradle/KGP 版本支持为准）；Kotlin daemon 内存合理配置。
- **语言特性成本**：
  - 大量 inline/内联多态与复杂泛型增加编译期类型检查压力——热库慎滥用巨型 inline；
  - KSP/注解处理与序列化插件的增量配置；
  - 避免在 api 模块放置无谓的巨型 sealed 层级强制全下游重编（变更敏感）。
- **流程**：编译时间监控（构建扫描/CI 曲线）、PR 级预算；IDE 与 CI 编译选项一致化。

### 【为什么这样设计】

编译速度是"依赖图 × 重编范围 × 单文件成本"三因子问题——模块边界与 API 稳定度决定图的形状，特性选择影响单点成本；治理靠架构决策而非只调 JVM 参数。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：增量命中、依赖环、拆分权衡、监控。
- 加分：给出"新模块准入"标准（大小、依赖数、变更频率）；与二进制兼容治理联动。
- 减分：一上来无限拆模块；只说开 daemon 不谈架构。

### 【追问链】

1. 何时拆？→ 编译/重编数据 + 团队 ownership；
2. 与 KMP？→ sourceSet 增加配置成本，需纳入预算；
3. 快速止血？→ 稳定核心 API、开构建缓存、清理无用依赖图边。

## 四、收束：tech lead 的 Kotlin 治理清单（速查）

- 空安全：边界注解统一、平台类型不穿透、反序列化校验；
- API：apiCheck 进 CI、弃用梯子、默认参数与 options 策略；
- 并发：作用域归属评审、禁 GlobalScope、异常与测试模板；
- 构建：模块按变更频率拆分、防依赖环、编译时间预算；
- 演进：试点→规范→工具强制，用数据反对流行度。
