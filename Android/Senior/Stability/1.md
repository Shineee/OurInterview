# 第1页 · 崩溃治理全链路

面向资深/专家面试：崩溃治理不是"接一个 Crash SDK"，而是**采集 → 归因 → 聚合 → 治理 → 验证**的闭环。本页讲采集与归因机制，第2页讲指标体系与放量。

## 一、Java 层崩溃采集与语义

### 问题

如何采集 Java 未捕获异常？为什么很多自研 handler 直接 `Process.killProcess` 是错的？

### 机制级答案

- 入口：`Thread.setDefaultUncaughtExceptionHandler`。异常线程为任意线程，但**绝大多数致命崩溃发生在主线程**。
- 正确姿势：自定义 handler 中「① 附加上下文（进程名、版本、自定义 key、生死簿快照）→ ② 同步落盘 pending 文件（防止进程随即死亡）→ ③ 调用 `preHandler.uncaughtException(t, e)` 交还系统默认 handler」。
- 交还的理由：系统默认 handler 完成「弹崩溃框（debuggable）→ 通知 AMS → 杀进程」的完整语义；吞掉异常或自定义 `killProcess`/`exitVM` 会造成：用户看到"应用无响应/闪退回桌面但无日志"、厂商崩溃统计与自家口径漂移、以及与系统 ActivityManager 的进程管理预期不一致。
- 子线程异常：同样走 default handler，但线程池场景建议 `ThreadPoolExecutor.afterExecute`、`Future.get` 包装 `ExecutionException`、或 `ThreadFactory` 统一包一层 try/catch——线程池里的"静默死"（任务失败但线程还活着）是 default handler 抓不到的。
- 与 AMS 的联动：Java 崩溃最终走 `RuntimeInit` 里注册的 handler 链；应用层永远在链上做**前置观测**，不替换链的终点。

### 【为什么这样设计】

监控是旁路系统，必须对宿主进程的崩溃语义保持敬畏——旁路只加信息、不改行为，是所有 APM SDK 的第一原则。

### 【面试官视角】

- 加分：区分 `Exception`（可恢复边界）与 `Error`（OOM/StackOverflow 通常不可继续）；提到主线程自定义 `Looper.loop` 拦截把业务异常降级为"吞掉+上报+继续"需逐项评审（只适合白名单可恢复场景）。
- 减分：主张"catch 所有异常让 App 不崩"。

### 【追问链】

1. OOM 和普通异常治理路径有何不同？→ OOM 要关联内存画像（堆快照/设备内存档位），不能只看堆栈首帧。
2. 如何抓到 `Executors` 默认线程池吞掉的异常？→ `afterExecute` + 无返回值任务的 `UncaughtExceptionHandler` 包装。

## 二、Native 崩溃采集

### 问题

Native crash（SIGSEGV 等）为什么比 Java 崩溃难抓？自研采集的正确边界在哪里？

### 机制级答案

- 常见信号：`SIGSEGV`（非法内存访问）、`SIGABRT`（abort，含 native 断言）、`SIGBUS`（对齐/映射错误）、`SIGFPE`、`SIGILL`、`SIGSTKFLT`（栈溢出相关）。
- 注册：`sigaction`，`SA_SIGINFO | SA_ONSTACK`，配合 `sigaltstack`——**栈溢出时原栈不可用**，必须有独立信号栈，否则 handler 自己先崩。
- handler 内纪律：只允许 async-signal-safe 操作（如 `write`、向预分配缓冲拷贝、`close`）。禁止：`malloc`、日志库、加锁（锁在崩溃时可能已被持有 → 死锁）、C++ 异常/iostream。正确流程是「**快照寄存器 + 上下文到预分配内存/文件 → 恢复默认 handler 或重新触发信号 → 让系统 debuggerd/tombstone 也能记录**」。
- 展开与符号化：在 handler 内做 DWARF/eh_frame unwind 成本高且不安全；工业方案（Breakpad/Crashpad 思路）是崩溃时写 minidump（含寄存器、线程栈、映射表、可选堆信息），**下次启动**在安全环境解析与符号化。so 需保留未 strip 的符号或上传符号表，线上包用独立符号化服务映射到源码行。
- Android 现实：系统自带 debuggerd/tombstone；自研 SDK 价值在于**带上业务维度**（自定义 key、生死簿、动态链接的业务 so 版本）并纳入自家聚合大盘。

### 【为什么这样设计】

崩溃瞬间进程状态不可信——"先保真快照、后异步加工"是唯一稳妥路径；符号化是 CPU/内存密集操作，必须移出崩溃路径。

### 【面试官视角】

- 加分：能说出信号安全清单的来源（POSIX async-signal-safe）；提到 JNI 层与纯 native 层栈的跨语言展开难点；提到 use-after-free 崩在 malloc 内部时要看"分配栈"而非"释放栈"。
- 减分：handler 里直接 `new`/`printf`/网络上报。

### 【追问链】

1. 如何提高 Native 死因归因率？→ 崩溃现场附带 maps、最近分配记录（采样式 malloc hook）、生死簿事件。
2. 为什么崩溃有时"无声无息"（logcat 无 tombstone）？→ 自杀式 signal、被系统 kill、或 handler 吞信号后进程状态已坏——SDK 需检测「上次 pending 文件存在但无退出记录」。

## 三、生死簿式监控（生命周期日志）

### 问题

只有崩溃堆栈，很多线上问题无法归因。什么是"生死簿"式监控？

### 机制级答案

- 定义：端上维护**环形缓冲**，持续记录带时间戳的关键事件，崩溃/ANR/ watchdog 触发时整段落盘、下次启动上报。记录项建议：
  - 进程/组件生命周期：Application 各阶段、Activity/Fragment create-start-resume-pause-stop-destroy、进程前后台切换；
  - 主线程：每条 Message 的 what/target/执行耗时（Looper logging）、心跳状态翻转；
  - 业务：路由跳转、关键网络请求开始/结束（URL 模板、状态码）、登录态变化；
  - 异常前兆：已捕获异常、信号未致命前的软失败。
- 成本控制：单条事件 ≤ 几十字节级别（int id + 短参数），环形容量 512~2048 条，内存占用 KB 级；不写全量、不记敏感数据（手机号/token 禁止入簿）。
- 用法：崩溃 case 中，堆栈 = 死点，生死簿 = 死前 30 秒时间线。例：死在 `libc.so` malloc → 生死簿显示前一条是大图加载 → 结合内存水位归因为 native 内存耗尽/踩踏而非"随机崩溃"。

### 【为什么这样设计】

崩溃分析本质是**分布式故障的事后考古**：样本只有一具"尸体"（进程），必须提前留下"行车记录仪"。这是对"现场不可复现"的工程补偿。

### 【面试官视角】

- 加分：给出隐私与容量红线；提到事件分级（必记/采样记）；能把生死簿与 ANR 心跳、路由埋点打通成一条时间线。
- 减分：把生死簿说成"打日志到文件"——没有环形上限、没有触发落盘协议、没有上报时机的"日志"在崩溃场景基本不可用。

### 【追问链】

1. 崩溃发生在落盘中途怎么办？→ 双缓冲 + 校验和，下次启动校验失败丢弃不完整段。
2. 与 `dropbox`/系统 log 的关系？→ 系统侧信息保留为旁证，生死簿补业务上下文，两层互补。

## 四、归因方法论（从堆栈到根因）

- **Java 崩溃**：首帧业务栈 → 检查空安全/并发修改/类型转换三类高频；跨端重复出现则查公共组件版本。
- **Native**：崩点所在 so 与信号 → 分配/释放/访问三方关系；结合符号化后的源码行。
- **OOM**：先分类（Java 堆 OOM / native OOM / FD 耗尽 / 线程数超限），再各走对应画像——"OOM = 堆泄漏"是常见误导。
- **ANR 死亡**：见第2页。

> 面试收束句："治理的终点不是崩溃率数字下降，而是**新指纹进入 TOP 榜单时，48 小时内有 owner、有归因、有修复版本或缓解开关**。"
