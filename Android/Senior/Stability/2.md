# 第2页 · ANR 归因与线上质量体系

## 一、ANR 机制与分类

### 问题

ANR 到底是谁判定的？不同类型 ANR 的超时与归因路径有什么不同？

### 机制级答案

- **判定方是系统，不是应用**。典型超时（历史口径，版本间以系统为准）：
  - Input dispatching timeout：输入事件 5s 未分发完（最常见，表现为点击/滑动无响应）；
  - Broadcast queue：前台广播 10s / 后台 60s（超时后 receiver 所在进程被杀）；
  - Service：前台服务 20s / 后台 200s（create/start/timeout 路径）；
  - ContentProvider publish：10s。
- 进程侧现象：主线程 Looper 无法及时处理消息；系统向进程发 `SIGQUIT` 触发 dump 主线程栈到 anr traces；随后按策略弹「应用无响应」或直接杀进程。
- 应用侧能做的不是"捕获"，而是：**预测（心跳）+ 事后取证（存活时主动 dump 栈 + 解析系统 traces）+ 事前预防（主线程纪律）**。

### 【为什么这样设计】

ANR 的本质是「主线程消息循环的时延超过系统对可交互性的承诺」。系统必须在用户砸手机前介入，所以超时判定权在系统侧；应用只能优化自己被观测到的时延。

## 二、ANR 归因实战路径

### 问题

拿到一个 ANR case，如何快速归因？

### 机制级答案（按主线程栈首帧特征分桶）

1. **Binder 阻塞/同步 IPC**：主线程栈出现 `BinderProxy.transactNative` 或 `acquireProvider`。
   - 成因：主线程同步调用远端（system_server 或自有多进程服务），远端繁忙/死锁/单线程队列堵塞；或 ContentProvider 查询未优化。
   - 排查：看对端进程同时间点的栈与 binder 线程池占用；检查是否把网络/磁盘操作放进被主线程同步调用的 AIDL 方法。**铁律：主线程禁止同步 binder 到自定义进程服务，服务端方法必须无 IO。**
2. **锁等待**：`Object.wait`、`ReentrantLock.lock`、`Condition.await`。
   - 成因：持锁方在后台线程做长 IO，主线程抢同一把锁；或跨进程锁（文件锁）被占用。
   - 排查：jstack/主动 dump 看**持有者线程**（Monitor 竞争信息），把等待图补全——只有主线程栈没有持锁栈会归因失败。
3. **主线程 IO**：栈在 `read`/`write`/`SharedPreferences.commit`/`SQLite`/`FileInputStream`。
   - 经典：`apply` 队列在 QueuedWork 里于 `onStop`/`onPause` 时被同步等待；`commit` 直接阻塞；首次读大文件 SP。
   - 治理：MMKV/DataStore 类方案、SP 异步化、把 IO 挪出主线程。
4. **锁竞争放大 + 消息风暴**：主线程栈正常但在 `Looper.loop` 取消息前——看生死簿里的单条消息耗时；常因一次分发内做了重活（RecyclerView 大 onBindViewHolder、序列化大对象）。
5. **系统侧**：主线程在等系统返回（`acquireProvider`、`ActivityManager` 相关 binder）——归因转移到 system_server（system_server 卡、输入焦点窗口异常、资源竞争）。

### 归因作业流（工业路径）

```
ANR 记录（进程名/时间/原因类型）
  → 对齐主线程栈（主动 dump 或 traces）
  → 补全锁持有者/binder 对端栈（同一时间窗）
  → 生死簿时间线（此前 30s 主线程消息耗时、路由、网络）
  → 分桶：应用自身 / 跨进程 / 系统侧
  → 指纹聚合进大盘
```

### 【面试官视角】

- 加分：提到"只有主线程栈不足以归因，必须补持锁线程/binder 对端"；提到 QueuedWork 与 SP；提到 Input ANR 与 Broadcast ANR 的分桶处理节奏不同。
- 减分：把卡顿（掉帧）与 ANR 混为一谈——卡顿是时延分布问题，ANR 是超阈值质变；把"主线程耗时 >16ms"都叫 ANR 风险而不谈分位与上限。

### 【追问链】

1. 如何预防 Broadcast ANR？→ 广播接收器只做标记与调度，重活转 JobScheduler/WorkManager；有序广播链上每个 receiver 都是超时贡献者。
2. 多少毫秒必 ANR？→ 无精确公式：主线程持续阻塞 >5s 输入必现；短任务叠加、CPU 饥饿、IO 抖动也会触发系统判定——用「单消息耗时分位 + 心跳翻转」做预测，而不是赌阈值。

## 三、线上监控指标体系

### 问题

如何定义崩溃/ANR/卡顿的线上指标口径，使大盘可信、可报警、可对比版本？

### 机制级答案

- **分母口径先行**：三种常见分母——启动次数、活跃设备数（日活会话）、使用时长。推荐：**崩溃率 = 发生崩溃的会话数 / 总会话数**（或按设备日），避免"重度用户多崩几次把率打高"的偏差；ANR 同理。所有口径写成文档并冻结，版本间对比才有意义。
- **核心指标**：
  - Java/Native 崩溃率（分指纹 TOP、分版本、分机型档位、分 OS 版本）；
  - ANR 率（系统判定口径 + SDK 心跳预测口径，两套并行，互相校准）；
  - 卡顿：主线程消息耗时 >700ms 的会话占比、掉帧率（见 Performance 第2页）、分位数（P50/P90/P99）而非均值；
  - 辅助：崩溃后重启成功率、修复版本的指纹消失率。
- **聚合维度**：版本 × 机型 × OS × 渠道 × 灰度分群；指纹级去重；异常突增用**环比/同比 + 控制组**识别（新版本放量期必须留对照组）。
- **报警**：新指纹进入 TOP、任一维度超基线 σ 倍、全网率抬升——分级到值班机器人与 owner。

### 【为什么这样设计】

指标体系的敌人是"分母漂移"和"维度塌缩"：没有会话分母，崩溃率不可比；没有分群对照，把自然波动当回归。稳定大盘是放量决策的前提。

### 【面试官视角】

- 加分：能指出"崩溃次数/启动次数"与"崩溃会话/总会话"的差异场景（重试风暴）；提到监控自身流量配额与采样对口径的修正公式。
- 减分：只背"崩溃率万分之X 达标"，说不出分母与分群。

## 四、灰度放量与熔断策略

### 问题

新版本/新监控/新通道如何放量？出问题如何自动止损？

### 机制级答案

- **分群放量阶梯**：内部 dogfood → 0.1% → 1% → 5% → 20% → 50% → 全量；每档观察 ≥ 1 个自然高峰周期（通常 24h，核心版本 48h）。
- **每档准入指标**：崩溃率、ANR 率不劣于对照组置信区间；性能关键指标（启动、掉帧分位）不回退超过约定阈值。
- **自动熔断**：端上/配置中心设规则——放量群体内核心指标抬升超过阈值 → 停止扩大放量；恶化超红线 → 远程开关回滚功能或整版本（整版本回滚依赖灰度包通道与应用市场节奏，端上开关回滚是更快路径）。**重要经验：新功能必须能被远程杀死**，否则放量等于裸奔。
- **监控自身的放量**：新采集（如 native 心跳、malloc 采样）也有崩溃风险——先白名单机型、再小比例，采集崩溃率单独考核。
- **回滚后动作**：保留现场（崩溃 pending、生死簿）→ 归因 → 修复后再走一轮阶梯；禁止"热修后直接全量"。

### 【为什么这样设计】

放量是用群体做真实世界的预生产验证；熔断是承认"测试环境永远测不全"。两者共同把线上事故的**爆炸半径**从全网缩小到单档人群，并把止损时间从"等用户投诉"压缩到"指标触发分钟级"。

### 【面试官视角】

- 加分：给出具体阈值示例与观察窗口；提到机型/OS 长尾要延长观察；提到开关粒度（功能级 > 版本级）。
- 减分：只有"先灰度再全量"口号，无指标、无窗口、无熔断动作。
