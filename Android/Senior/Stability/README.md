# Stability

面向资深/专家面试：崩溃治理不是"接一个 Crash SDK"，而是**采集 → 归因 → 聚合 → 治理 → 验证**的闭环。本页讲采集与归因机制，第2页讲指标体系与放量。

## 一、Java 层崩溃采集与语义

### 问题

如何采集 Java 未捕获异常？为什么很多自研 handler 直接 `Process.killProcess` 是错的？

### 机制级答案

- 入口：`Thread.setDefaultUncaughtExceptionHandler`。异常线程为任意线程，但**绝大多数致命崩溃发生在主线程**。
- 正确姿势：自定义 handler 中「① 附加上下文（进程名、版本、自定义 key、生死簿快照）→ ② 同步落盘 pending 文件（防止进程随即死亡）→ ③ 调用 `preHandler.uncaughtException(t, e)` 交还系统默认 handler」。
- 交还的理由：系统默认 handler 完成「弹崩溃框（debuggable）→ 通知 AMS → 杀进程」的完整语义；吞掉异常或自定义 `killProcess`/`exitVM` 会造成：用户看到"应用无响应/闪退回桌面但无日志"、厂商崩溃统计与自家口径漂移、以及与系统 ActivityManager 的进程管理预期不一致。
- 子线程异常：同样走 default handler，但线程池场景建议 `ThreadPoolExecutor.afterExecute`、`Future.get` 包装 `ExecutionException`、或 `ThreadFactory` 统一包一层 try/catch——线程池里的"静默死"（任务失败但线程还活着）是 default handler 抓不到的。
- 与 AMS 的联动：Java 崩溃最终走 `RuntimeInit` 里注册的 handler 链；应用层永远在链上做**前置观测**，不替换链的终点。

### 【为什么这样设计】

监控是旁路系统，必须对宿主进程的崩溃语义保持敬畏——旁路只加信息、不改行为，是所有 APM SDK 的第一原则。

### 【面试官视角】

- 加分：区分 `Exception`（可恢复边界）与 `Error`（OOM/StackOverflow 通常不可继续）；提到主线程自定义 `Looper.loop` 拦截把业务异常降级为"吞掉+上报+继续"需逐项评审（只适合白名单可恢复场景）。
- 减分：主张"catch 所有异常让 App 不崩"。

### 【追问链】

1. OOM 和普通异常治理路径有何不同？→ OOM 要关联内存画像（堆快照/设备内存档位），不能只看堆栈首帧。
2. 如何抓到 `Executors` 默认线程池吞掉的异常？→ `afterExecute` + 无返回值任务的 `UncaughtExceptionHandler` 包装。

## 二、Native 崩溃采集

### 问题

Native crash（SIGSEGV 等）为什么比 Java 崩溃难抓？自研采集的正确边界在哪里？

### 机制级答案

- 常见信号：`SIGSEGV`（非法内存访问）、`SIGABRT`（abort，含 native 断言）、`SIGBUS`（对齐/映射错误）、`SIGFPE`、`SIGILL`、`SIGSTKFLT`（栈溢出相关）。
- 注册：`sigaction`，`SA_SIGINFO | SA_ONSTACK`，配合 `sigaltstack`——**栈溢出时原栈不可用**，必须有独立信号栈，否则 handler 自己先崩。
- handler 内纪律：只允许 async-signal-safe 操作（如 `write`、向预分配缓冲拷贝、`close`）。禁止：`malloc`、日志库、加锁（锁在崩溃时可能已被持有 → 死锁）、C++ 异常/iostream。正确流程是「**快照寄存器 + 上下文到预分配内存/文件 → 恢复默认 handler 或重新触发信号 → 让系统 debuggerd/tombstone 也能记录**」。
- 展开与符号化：在 handler 内做 DWARF/eh_frame unwind 成本高且不安全；工业方案（Breakpad/Crashpad 思路）是崩溃时写 minidump（含寄存器、线程栈、映射表、可选堆信息），**下次启动**在安全环境解析与符号化。so 需保留未 strip 的符号或上传符号表，线上包用独立符号化服务映射到源码行。
- Android 现实：系统自带 debuggerd/tombstone；自研 SDK 价值在于**带上业务维度**（自定义 key、生死簿、动态链接的业务 so 版本）并纳入自家聚合大盘。

### 【为什么这样设计】

崩溃瞬间进程状态不可信——"先保真快照、后异步加工"是唯一稳妥路径；符号化是 CPU/内存密集操作，必须移出崩溃路径。

### 【面试官视角】

- 加分：能说出信号安全清单的来源（POSIX async-signal-safe）；提到 JNI 层与纯 native 层栈的跨语言展开难点；提到 use-after-free 崩在 malloc 内部时要看"分配栈"而非"释放栈"。
- 减分：handler 里直接 `new`/`printf`/网络上报。

### 【追问链】

1. 如何提高 Native 死因归因率？→ 崩溃现场附带 maps、最近分配记录（采样式 malloc hook）、生死簿事件。
2. 为什么崩溃有时"无声无息"（logcat 无 tombstone）？→ 自杀式 signal、被系统 kill、或 handler 吞信号后进程状态已坏——SDK 需检测「上次 pending 文件存在但无退出记录」。

## 三、生死簿式监控（生命周期日志）

### 问题

只有崩溃堆栈，很多线上问题无法归因。什么是"生死簿"式监控？

### 机制级答案

- 定义：端上维护**环形缓冲**，持续记录带时间戳的关键事件，崩溃/ANR/ watchdog 触发时整段落盘、下次启动上报。记录项建议：
  - 进程/组件生命周期：Application 各阶段、Activity/Fragment create-start-resume-pause-stop-destroy、进程前后台切换；
  - 主线程：每条 Message 的 what/target/执行耗时（Looper logging）、心跳状态翻转；
  - 业务：路由跳转、关键网络请求开始/结束（URL 模板、状态码）、登录态变化；
  - 异常前兆：已捕获异常、信号未致命前的软失败。
- 成本控制：单条事件 ≤ 几十字节级别（int id + 短参数），环形容量 512~2048 条，内存占用 KB 级；不写全量、不记敏感数据（手机号/token 禁止入簿）。
- 用法：崩溃 case 中，堆栈 = 死点，生死簿 = 死前 30 秒时间线。例：死在 `libc.so` malloc → 生死簿显示前一条是大图加载 → 结合内存水位归因为 native 内存耗尽/踩踏而非"随机崩溃"。

### 【为什么这样设计】

崩溃分析本质是**分布式故障的事后考古**：样本只有一具"尸体"（进程），必须提前留下"行车记录仪"。这是对"现场不可复现"的工程补偿。

### 【面试官视角】

- 加分：给出隐私与容量红线；提到事件分级（必记/采样记）；能把生死簿与 ANR 心跳、路由埋点打通成一条时间线。
- 减分：把生死簿说成"打日志到文件"——没有环形上限、没有触发落盘协议、没有上报时机的"日志"在崩溃场景基本不可用。

### 【追问链】

1. 崩溃发生在落盘中途怎么办？→ 双缓冲 + 校验和，下次启动校验失败丢弃不完整段。
2. 与 `dropbox`/系统 log 的关系？→ 系统侧信息保留为旁证，生死簿补业务上下文，两层互补。

## 四、归因方法论（从堆栈到根因）

- **Java 崩溃**：首帧业务栈 → 检查空安全/并发修改/类型转换三类高频；跨端重复出现则查公共组件版本。
- **Native**：崩点所在 so 与信号 → 分配/释放/访问三方关系；结合符号化后的源码行。
- **OOM**：先分类（Java 堆 OOM / native OOM / FD 耗尽 / 线程数超限），再各走对应画像——"OOM = 堆泄漏"是常见误导。
- **ANR 死亡**：见第2页。

> 面试收束句："治理的终点不是崩溃率数字下降，而是**新指纹进入 TOP 榜单时，48 小时内有 owner、有归因、有修复版本或缓解开关**。"

## 一、ANR 机制与分类

### 问题

ANR 到底是谁判定的？不同类型 ANR 的超时与归因路径有什么不同？

### 机制级答案

- **判定方是系统，不是应用**。典型超时（历史口径，版本间以系统为准）：
  - Input dispatching timeout：输入事件 5s 未分发完（最常见，表现为点击/滑动无响应）；
  - Broadcast queue：前台广播 10s / 后台 60s（超时后 receiver 所在进程被杀）；
  - Service：前台服务 20s / 后台 200s（create/start/timeout 路径）；
  - ContentProvider publish：10s。
- 进程侧现象：主线程 Looper 无法及时处理消息；系统向进程发 `SIGQUIT` 触发 dump 主线程栈到 anr traces；随后按策略弹「应用无响应」或直接杀进程。
- 应用侧能做的不是"捕获"，而是：**预测（心跳）+ 事后取证（存活时主动 dump 栈 + 解析系统 traces）+ 事前预防（主线程纪律）**。

### 【为什么这样设计】

ANR 的本质是「主线程消息循环的时延超过系统对可交互性的承诺」。系统必须在用户砸手机前介入，所以超时判定权在系统侧；应用只能优化自己被观测到的时延。

## 二、ANR 归因实战路径

### 问题

拿到一个 ANR case，如何快速归因？

### 机制级答案（按主线程栈首帧特征分桶）

1. **Binder 阻塞/同步 IPC**：主线程栈出现 `BinderProxy.transactNative` 或 `acquireProvider`。
   - 成因：主线程同步调用远端（system_server 或自有多进程服务），远端繁忙/死锁/单线程队列堵塞；或 ContentProvider 查询未优化。
   - 排查：看对端进程同时间点的栈与 binder 线程池占用；检查是否把网络/磁盘操作放进被主线程同步调用的 AIDL 方法。**铁律：主线程禁止同步 binder 到自定义进程服务，服务端方法必须无 IO。**
2. **锁等待**：`Object.wait`、`ReentrantLock.lock`、`Condition.await`。
   - 成因：持锁方在后台线程做长 IO，主线程抢同一把锁；或跨进程锁（文件锁）被占用。
   - 排查：jstack/主动 dump 看**持有者线程**（Monitor 竞争信息），把等待图补全——只有主线程栈没有持锁栈会归因失败。
3. **主线程 IO**：栈在 `read`/`write`/`SharedPreferences.commit`/`SQLite`/`FileInputStream`。
   - 经典：`apply` 队列在 QueuedWork 里于 `onStop`/`onPause` 时被同步等待；`commit` 直接阻塞；首次读大文件 SP。
   - 治理：MMKV/DataStore 类方案、SP 异步化、把 IO 挪出主线程。
4. **锁竞争放大 + 消息风暴**：主线程栈正常但在 `Looper.loop` 取消息前——看生死簿里的单条消息耗时；常因一次分发内做了重活（RecyclerView 大 onBindViewHolder、序列化大对象）。
5. **系统侧**：主线程在等系统返回（`acquireProvider`、`ActivityManager` 相关 binder）——归因转移到 system_server（system_server 卡、输入焦点窗口异常、资源竞争）。

### 归因作业流（工业路径）

```
ANR 记录（进程名/时间/原因类型）
  → 对齐主线程栈（主动 dump 或 traces）
  → 补全锁持有者/binder 对端栈（同一时间窗）
  → 生死簿时间线（此前 30s 主线程消息耗时、路由、网络）
  → 分桶：应用自身 / 跨进程 / 系统侧
  → 指纹聚合进大盘
```

### 【面试官视角】

- 加分：提到"只有主线程栈不足以归因，必须补持锁线程/binder 对端"；提到 QueuedWork 与 SP；提到 Input ANR 与 Broadcast ANR 的分桶处理节奏不同。
- 减分：把卡顿（掉帧）与 ANR 混为一谈——卡顿是时延分布问题，ANR 是超阈值质变；把"主线程耗时 >16ms"都叫 ANR 风险而不谈分位与上限。

### 【追问链】

1. 如何预防 Broadcast ANR？→ 广播接收器只做标记与调度，重活转 JobScheduler/WorkManager；有序广播链上每个 receiver 都是超时贡献者。
2. 多少毫秒必 ANR？→ 无精确公式：主线程持续阻塞 >5s 输入必现；短任务叠加、CPU 饥饿、IO 抖动也会触发系统判定——用「单消息耗时分位 + 心跳翻转」做预测，而不是赌阈值。

## 三、线上监控指标体系

### 问题

如何定义崩溃/ANR/卡顿的线上指标口径，使大盘可信、可报警、可对比版本？

### 机制级答案

- **分母口径先行**：三种常见分母——启动次数、活跃设备数（日活会话）、使用时长。推荐：**崩溃率 = 发生崩溃的会话数 / 总会话数**（或按设备日），避免"重度用户多崩几次把率打高"的偏差；ANR 同理。所有口径写成文档并冻结，版本间对比才有意义。
- **核心指标**：
  - Java/Native 崩溃率（分指纹 TOP、分版本、分机型档位、分 OS 版本）；
  - ANR 率（系统判定口径 + SDK 心跳预测口径，两套并行，互相校准）；
  - 卡顿：主线程消息耗时 >700ms 的会话占比、掉帧率（见 Performance 第2页）、分位数（P50/P90/P99）而非均值；
  - 辅助：崩溃后重启成功率、修复版本的指纹消失率。
- **聚合维度**：版本 × 机型 × OS × 渠道 × 灰度分群；指纹级去重；异常突增用**环比/同比 + 控制组**识别（新版本放量期必须留对照组）。
- **报警**：新指纹进入 TOP、任一维度超基线 σ 倍、全网率抬升——分级到值班机器人与 owner。

### 【为什么这样设计】

指标体系的敌人是"分母漂移"和"维度塌缩"：没有会话分母，崩溃率不可比；没有分群对照，把自然波动当回归。稳定大盘是放量决策的前提。

### 【面试官视角】

- 加分：能指出"崩溃次数/启动次数"与"崩溃会话/总会话"的差异场景（重试风暴）；提到监控自身流量配额与采样对口径的修正公式。
- 减分：只背"崩溃率万分之X 达标"，说不出分母与分群。

## 四、灰度放量与熔断策略

### 问题

新版本/新监控/新通道如何放量？出问题如何自动止损？

### 机制级答案

- **分群放量阶梯**：内部 dogfood → 0.1% → 1% → 5% → 20% → 50% → 全量；每档观察 ≥ 1 个自然高峰周期（通常 24h，核心版本 48h）。
- **每档准入指标**：崩溃率、ANR 率不劣于对照组置信区间；性能关键指标（启动、掉帧分位）不回退超过约定阈值。
- **自动熔断**：端上/配置中心设规则——放量群体内核心指标抬升超过阈值 → 停止扩大放量；恶化超红线 → 远程开关回滚功能或整版本（整版本回滚依赖灰度包通道与应用市场节奏，端上开关回滚是更快路径）。**重要经验：新功能必须能被远程杀死**，否则放量等于裸奔。
- **监控自身的放量**：新采集（如 native 心跳、malloc 采样）也有崩溃风险——先白名单机型、再小比例，采集崩溃率单独考核。
- **回滚后动作**：保留现场（崩溃 pending、生死簿）→ 归因 → 修复后再走一轮阶梯；禁止"热修后直接全量"。

### 【为什么这样设计】

放量是用群体做真实世界的预生产验证；熔断是承认"测试环境永远测不全"。两者共同把线上事故的**爆炸半径**从全网缩小到单档人群，并把止损时间从"等用户投诉"压缩到"指标触发分钟级"。

### 【面试官视角】

- 加分：给出具体阈值示例与观察窗口；提到机型/OS 长尾要延长观察；提到开关粒度（功能级 > 版本级）。
- 减分：只有"先灰度再全量"口号，无指标、无窗口、无熔断动作。
