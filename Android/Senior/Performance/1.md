# 第1页 · 启动优化体系

面向资深/专家面试：启动优化不是"把初始化挪个线程"，而是**测量口径 → 任务编排 → 预加载 → 度量回归**的体系工程。

## 一、测量口径（先定义，再优化）

### 问题

启动耗时有进程启动、首帧、可交互、TTI、FullyDrawn 等多个口径，面试如何答？

### 机制级答案

- **系统视角**：进程 fork（zygote）→ `Application.onCreate` → 首个 Activity 生命周期 → 首帧上屏（`ViewRootImpl` 完成 `performTraversals` 的 draw）。adb 侧历史口径：`am start -W` 给出 `WaitTime`（含系统侧）与 `TotalTime`；Trace 侧看 `reportFullyDrawn`（应用主动上报"内容真正可看"，如列表数据渲染完）。
- **建议口径组合**（对内统一后再比版本）：
  1. 冷启动端到端（进程创建 → 首帧）：系统+应用合计，对外宣传慎用；
  2. Application 阶段耗时（`attachBaseContext`→`onCreate` 结束）：应用可控主战场；
  3. 首页首帧后关键内容就绪（自定义 FullyDrawn）：贴近用户感知；
  4. 可交互（首帧 + 主线程消息队列排空到空闲）：与卡顿/ANR 体系衔接。
- **分解工具**：Perfetto/systrace 看进程启动切片、类加载、binder、IO；应用内插桩把 onCreate 拆成任务级耗时。**没有任务级耗时分布就做优化，等于盲人摸象。**
- **环境因子**：机型档位、存储 IO 健康度、是否首次安装、后台干扰——大盘对比必须同档位分组，否则噪声淹没收益。

### 【为什么这样设计】

"优化 100ms"只有在固定口径下才可证伪；多口径并存是因为系统调度的启动与用户感知的"能用"不是同一事件——专家要能说清每个口径的适用边界。

### 【面试官视角】

- 加分：主动区分冷/热/温启动；提到 `reportFullyDrawn` 与商店/系统的性能面板口径差异；给出自家 App 的任务级耗时示例结构（如某 SDK 初始化占 120ms）。
- 减分：只说"用 adb 测启动时间"，被追问口径立刻含糊。

### 【追问链】

1. 为什么有时优化后 adb 时间没变但用户觉得变快？→ 优化的是 FullyDrawn/可交互，不是 WaitTime；口径要对齐叙事。
2. 大盘如何持续回归？→ 线上分位数（P50/P90）按版本+机型档位看板，放量期对照组。

## 二、主线程任务编排

### 问题

Application 里几十个 SDK 初始化互相有依赖，如何组织主线程任务？

### 机制级答案

- **建模为 DAG**：每个初始化任务声明 `deps`（前置）与 `thread`（main/async）；拓扑排序后主线程只跑「必须主线程 + 被首帧关键路径依赖」的子图，其余丢到后台线程池按层并行。
- **主线程任务准入标准**：与四大组件/主线程 Handler 强绑定、需要在 `onCreate` 返回前完成的 UI 相关初始化、必须主线程注册的回调（如部分推送、部分监控的默认 handler）。其余默认后台，**举证倒置**（想留在主线程要说明理由）。
- **异步化陷阱**（面试必讲）：
  - 依赖被打破：后台初始化尚未完成，主线程就使用 → 加 await/门闩，但 await 本身可能阻塞主线程——用**可挂起的延迟使用**（代理/懒加载）优于阻塞等待；
  - 生命周期竞争：`onCreate` 结束后任务仍在跑，Activity 已用到未就绪组件；
  - 线程安全：初始化与使用方之间的 happens-before 要靠同步原语建立，不能裸奔。
- **工程形态**：启动任务框架（自研或参考 App Startup / 各大厂 task 编排）+ 可视化依赖图 + 耗时红线（如单任务主线程 >20ms 告警）。App Startup 解决的是 `ContentProvider` 式初始化的多 provider 开销与顺序不可控问题，本质仍是显式编排。

### 【为什么这样设计】

启动路径是**全局串行关键路径**：主线程上每一毫秒都直接计入用户等待；把无依赖任务并行化、把非关键任务推迟到首帧后（IdleHandler / 首帧回调），是把"串行关键路径"压缩为"最小必要子图"。

### 【面试官视角】

- 加分：画出 DAG 并讨论环依赖检测；提到"延迟初始化 + 使用处代理"模式；提到多进程 App 只初始化该进程用到的任务（进程级任务清单）。
- 减分：把所有 SDK 丢 `Thread` 里就宣布优化完成——无依赖建模、无 await 语义，是隐性崩溃源。

### 【追问链】

1. 首帧后还有大量任务怎么办？→ 分级：首帧后空闲（IdleHandler）、进入首页后、首次业务触发时；配超时兜底强制完成关键项。
2. 如何防止任务框架自己变慢？→ 框架本身零反射、加载表用编译期生成；框架耗时单独埋点。

## 三、类预加载与 so 预加载

### 问题

类加载与 JNI 库加载在启动中的开销如何治理？

### 机制级答案

- **类加载开销来源**：dex 查找、verify/prepare、静态初始化。热点类在主线程首次触碰时付出成本。
- **预加载思路**：在子线程"预热"关键类（`Class.forName` 或 触发其静态路径），使其在主线程真正使用前完成加载——注意：**初始化有顺序与副作用**，盲目批量 forName 会触发大量静态构造与间接依赖，反而变慢；应从主线程 trace 的 `class load` 切片提取真实热点清单。
- **App Image / baseline profile**：安装时/系统侧生成 ART profile（热方法/热类），配合 `baseline-prof.txt`（Jetpack Baseline Profiles）让 ART 在安装或首次编译时对热路径做 AOT——这不是"自己 forName"，而是**把 JIT 热点固化**，对冷启动与列表滚动同时有效。Android 官方 Baseline Profile 机制是当前版本叙事的加分项。
- **so 预加载**：`System.loadLibrary` 成本 = 文件 IO + 重定位 + init 函数（JNI_OnLoad）。治理：合并稀碎 so、按需加载（插件/特性开关）、`JNI_OnLoad` 里只做注册不做重逻辑、避免在 onCreate 串行 load 多个大 so。多进程时注意：每个进程各自 load，内存映射不可跨进程直接复用（file-backed 页可共享只读段，但每个进程仍有映射与重定位成本）。
- **禁止事项**：不要在预加载线程做网络/磁盘重 IO；不要用预加载掩盖本该砍掉的初始化。

### 【为什么这样设计】

类与 so 的加载成本具有**可预测性**（同一代码路径在同机型上高度稳定），因此可以用预热与 AOT 提前支付；但预热清单必须来自测量，否则就是用不确定的猜测对抗确定的开销。

### 【面试官视角】

- 加分：区分 "预加载类"、"预热 JIT/AOT（baseline profile）"、"预创建实例" 三层；提到 ART profile 与 Cloud Profiles/安装时编译。
- 减分：把 `Class.forName` 当作万能药；不知道 `JNI_OnLoad` 与动态注册。

### 【追问链】

1. baseline profile 放哪个模块？如何验证生效？→ 放 app 或共享 feature 模块；用 Perfetto 看编译与启动切片、Play 商店的编译状态、或 `adb shell dumpsys package` 相关编译信息辅助。
2. 多 dex / 多进程下预加载清单要不要拆？→ 要：按进程拆清单，避免推送进程加载 UI 重类。

## 四、启动任务框架设计题模板

若面试官直接出"设计一个启动任务框架"：

1. **需求**：支持依赖声明、线程指定、超时、埋点、多进程清单、动态开关（远程可关某任务）。
2. **模型**：Task（id/deps/thread/timeout/cost）+ DAG 调度器 + 主线程泵（主线程任务队列 + 异步层并行）。
3. **正确性**：环检测失败 CI 报错；跨线程 await 有超时与降级；任务失败隔离（单任务异常不拖垮启动）。
4. **度量**：框架自报任务级耗时进大盘；启动关键路径红线告警。
5. **演进**：静态表 → 编译期生成依赖表 → 与 Baseline Profile、多进程懒加载清单联动。

> 收束句："启动优化的上限是**系统与业务的共同关键路径**，框架的职责是保证关键路径上没有私货、没有顺序事故，并让每毫秒可归因。"
