# Performance

面向资深/专家面试：启动优化不是"把初始化挪个线程"，而是**测量口径 → 任务编排 → 预加载 → 度量回归**的体系工程。

## 一、测量口径（先定义，再优化）

### 问题

启动耗时有进程启动、首帧、可交互、TTI、FullyDrawn 等多个口径，面试如何答？

### 机制级答案

- **系统视角**：进程 fork（zygote）→ `Application.onCreate` → 首个 Activity 生命周期 → 首帧上屏（`ViewRootImpl` 完成 `performTraversals` 的 draw）。adb 侧历史口径：`am start -W` 给出 `WaitTime`（含系统侧）与 `TotalTime`；Trace 侧看 `reportFullyDrawn`（应用主动上报"内容真正可看"，如列表数据渲染完）。
- **建议口径组合**（对内统一后再比版本）：
  1. 冷启动端到端（进程创建 → 首帧）：系统+应用合计，对外宣传慎用；
  2. Application 阶段耗时（`attachBaseContext`→`onCreate` 结束）：应用可控主战场；
  3. 首页首帧后关键内容就绪（自定义 FullyDrawn）：贴近用户感知；
  4. 可交互（首帧 + 主线程消息队列排空到空闲）：与卡顿/ANR 体系衔接。
- **分解工具**：Perfetto/systrace 看进程启动切片、类加载、binder、IO；应用内插桩把 onCreate 拆成任务级耗时。**没有任务级耗时分布就做优化，等于盲人摸象。**
- **环境因子**：机型档位、存储 IO 健康度、是否首次安装、后台干扰——大盘对比必须同档位分组，否则噪声淹没收益。

### 【为什么这样设计】

"优化 100ms"只有在固定口径下才可证伪；多口径并存是因为系统调度的启动与用户感知的"能用"不是同一事件——专家要能说清每个口径的适用边界。

### 【面试官视角】

- 加分：主动区分冷/热/温启动；提到 `reportFullyDrawn` 与商店/系统的性能面板口径差异；给出自家 App 的任务级耗时示例结构（如某 SDK 初始化占 120ms）。
- 减分：只说"用 adb 测启动时间"，被追问口径立刻含糊。

### 【追问链】

1. 为什么有时优化后 adb 时间没变但用户觉得变快？→ 优化的是 FullyDrawn/可交互，不是 WaitTime；口径要对齐叙事。
2. 大盘如何持续回归？→ 线上分位数（P50/P90）按版本+机型档位看板，放量期对照组。

## 二、主线程任务编排

### 问题

Application 里几十个 SDK 初始化互相有依赖，如何组织主线程任务？

### 机制级答案

- **建模为 DAG**：每个初始化任务声明 `deps`（前置）与 `thread`（main/async）；拓扑排序后主线程只跑「必须主线程 + 被首帧关键路径依赖」的子图，其余丢到后台线程池按层并行。
- **主线程任务准入标准**：与四大组件/主线程 Handler 强绑定、需要在 `onCreate` 返回前完成的 UI 相关初始化、必须主线程注册的回调（如部分推送、部分监控的默认 handler）。其余默认后台，**举证倒置**（想留在主线程要说明理由）。
- **异步化陷阱**（面试必讲）：
  - 依赖被打破：后台初始化尚未完成，主线程就使用 → 加 await/门闩，但 await 本身可能阻塞主线程——用**可挂起的延迟使用**（代理/懒加载）优于阻塞等待；
  - 生命周期竞争：`onCreate` 结束后任务仍在跑，Activity 已用到未就绪组件；
  - 线程安全：初始化与使用方之间的 happens-before 要靠同步原语建立，不能裸奔。
- **工程形态**：启动任务框架（自研或参考 App Startup / 各大厂 task 编排）+ 可视化依赖图 + 耗时红线（如单任务主线程 >20ms 告警）。App Startup 解决的是 `ContentProvider` 式初始化的多 provider 开销与顺序不可控问题，本质仍是显式编排。

### 【为什么这样设计】

启动路径是**全局串行关键路径**：主线程上每一毫秒都直接计入用户等待；把无依赖任务并行化、把非关键任务推迟到首帧后（IdleHandler / 首帧回调），是把"串行关键路径"压缩为"最小必要子图"。

### 【面试官视角】

- 加分：画出 DAG 并讨论环依赖检测；提到"延迟初始化 + 使用处代理"模式；提到多进程 App 只初始化该进程用到的任务（进程级任务清单）。
- 减分：把所有 SDK 丢 `Thread` 里就宣布优化完成——无依赖建模、无 await 语义，是隐性崩溃源。

### 【追问链】

1. 首帧后还有大量任务怎么办？→ 分级：首帧后空闲（IdleHandler）、进入首页后、首次业务触发时；配超时兜底强制完成关键项。
2. 如何防止任务框架自己变慢？→ 框架本身零反射、加载表用编译期生成；框架耗时单独埋点。

## 三、类预加载与 so 预加载

### 问题

类加载与 JNI 库加载在启动中的开销如何治理？

### 机制级答案

- **类加载开销来源**：dex 查找、verify/prepare、静态初始化。热点类在主线程首次触碰时付出成本。
- **预加载思路**：在子线程"预热"关键类（`Class.forName` 或 触发其静态路径），使其在主线程真正使用前完成加载——注意：**初始化有顺序与副作用**，盲目批量 forName 会触发大量静态构造与间接依赖，反而变慢；应从主线程 trace 的 `class load` 切片提取真实热点清单。
- **App Image / baseline profile**：安装时/系统侧生成 ART profile（热方法/热类），配合 `baseline-prof.txt`（Jetpack Baseline Profiles）让 ART 在安装或首次编译时对热路径做 AOT——这不是"自己 forName"，而是**把 JIT 热点固化**，对冷启动与列表滚动同时有效。Android 官方 Baseline Profile 机制是当前版本叙事的加分项。
- **so 预加载**：`System.loadLibrary` 成本 = 文件 IO + 重定位 + init 函数（JNI_OnLoad）。治理：合并稀碎 so、按需加载（插件/特性开关）、`JNI_OnLoad` 里只做注册不做重逻辑、避免在 onCreate 串行 load 多个大 so。多进程时注意：每个进程各自 load，内存映射不可跨进程直接复用（file-backed 页可共享只读段，但每个进程仍有映射与重定位成本）。
- **禁止事项**：不要在预加载线程做网络/磁盘重 IO；不要用预加载掩盖本该砍掉的初始化。

### 【为什么这样设计】

类与 so 的加载成本具有**可预测性**（同一代码路径在同机型上高度稳定），因此可以用预热与 AOT 提前支付；但预热清单必须来自测量，否则就是用不确定的猜测对抗确定的开销。

### 【面试官视角】

- 加分：区分 "预加载类"、"预热 JIT/AOT（baseline profile）"、"预创建实例" 三层；提到 ART profile 与 Cloud Profiles/安装时编译。
- 减分：把 `Class.forName` 当作万能药；不知道 `JNI_OnLoad` 与动态注册。

### 【追问链】

1. baseline profile 放哪个模块？如何验证生效？→ 放 app 或共享 feature 模块；用 Perfetto 看编译与启动切片、Play 商店的编译状态、或 `adb shell dumpsys package` 相关编译信息辅助。
2. 多 dex / 多进程下预加载清单要不要拆？→ 要：按进程拆清单，避免推送进程加载 UI 重类。

## 四、启动任务框架设计题模板

若面试官直接出"设计一个启动任务框架"：

1. **需求**：支持依赖声明、线程指定、超时、埋点、多进程清单、动态开关（远程可关某任务）。
2. **模型**：Task（id/deps/thread/timeout/cost）+ DAG 调度器 + 主线程泵（主线程任务队列 + 异步层并行）。
3. **正确性**：环检测失败 CI 报错；跨线程 await 有超时与降级；任务失败隔离（单任务异常不拖垮启动）。
4. **度量**：框架自报任务级耗时进大盘；启动关键路径红线告警。
5. **演进**：静态表 → 编译期生成依赖表 → 与 Baseline Profile、多进程懒加载清单联动。

> 收束句："启动优化的上限是**系统与业务的共同关键路径**，框架的职责是保证关键路径上没有私货、没有顺序事故，并让每毫秒可归因。"

---

三线并行的日常性能治理：内存决定稳定性与进程存活性，流畅度决定体验口碑，包体积决定转化与更新率。每条线都按「机制 → 度量 → 手段 → 面试官视角」组织。

## 一、内存

### 1.1 Ashmem 与共享内存（机制级）

- **Ashmem**（Android Shared Memory）：内核 ashmem 驱动提供可锁定、可按名映射的共享内存；用户态入口是 `MemoryFile` / `SharedMemory`（API 27+）/ NDK `ASharedMemory`。特点：可被 pin 住防止被回收压缩；可跨进程传递 fd。
- **用途场景**：跨进程传大块数据绕开 Binder 事务限制（1MB 事务上限是常见坑）；图形/媒体 buffer 语义（更底层是 GraphicBuffer/ION/dmabuf 体系，面试点到层次即可）；保活场景下的精简序列化。
- **与 Java 堆关系**：Ashmem 上的字节不在 dalvik 堆里——**Java 堆 OOM 时它不背锅，但进程 RSS/VSS 与系统 LMK 压力会算它**。

### 1.2 堆外与内存水位（机制级）

- 端上"内存"至少四层：Java 堆、Native 堆（malloc）、图形相关（纹理/buffer/合成）、文件映射（so/dex/资源）。Bitmap 在现代版本落在 Native（API 26+），只盯 Java 堆会漏诊。
- 度量：`Debug.MemoryInfo` / `Runtime` 堆统计 + `meminfo`  dumpsys 的 PSS/RSS；Native 堆用 malloc 调试（malloc_info、heapprofd/Perfetto 采样）。
- LMK/PSI：系统按 oom_adj 与内存压力杀进程；端上目标是「峰值驻留可控 + 不成为 adj 顶格进程的内存大户」。

### 1.3 泄漏监控与排查（高频考点）

- **原理（LeakCanary 思路）**：注册 `watch` 的对象在预期生命周期结束（如 Activity destroy）后入引用队列；主动触发 GC 后若仍能从 GC roots 强引用链到达该对象 → 判泄漏，采集 hprof → 解析最短引用链（到泄漏对象的 path to GC roots，剪掉系统已知噪声）→ 通知。
- **排查路径**：hprof → MAT/Android Studio Profiler：支配树（Dominator Tree）找大对象与异常持有 → path to GC roots（exclude weak/soft）→ 定位是静态集合/未反注册的监听/单例持 Context/内部类隐式引用哪一类。
- **常见根因桶**：静态持有 Activity/Context；监听器/回调未在 destroy 反注册；Handler/匿名内部类持外部；线程池任务持旧页面对象；Resource 泄漏（TypedArray.recycle 类）。
- **治理**：泄漏指纹化进大盘（Stability 第1页体系复用）；关键页面自动化泄漏检测（CI 跑 monkey + dump）。

#### 【面试官视角 · 内存】

- 加分：分层讲清 Java/Native/图形/映射；提到 Bitmap 新旧版本落点差异；给出「先分桶再深挖」的排查树。
- 减分：只会说 LeakCanary 名字；把所有 OOM 都归为"内存泄漏"。

#### 【追问链】

1. 如何区分泄漏与瞬时峰值？→ 泄漏看对象数随生命周期单调增长；峰值看曲线回落。多做多次 GC 后的堆对比。
2. Native 泄漏怎么查？→ heapprofd 采样分配栈，对可疑 so 做前后快照 diff。

## 二、流畅度（帧与合成）

### 2.1 帧生产管线（机制级）

- 垂直同步信号（VSYNC）驱动下，主线程 measure/layout/draw 产出 DisplayList，RenderThread（API 级）执行 GPU 指令，SurfaceFlinger 合成上屏。一帧预算：60Hz ≈ 16.6ms，90/120Hz 相应更紧。
- **掉帧**：当帧未在对应 VSYNC 周期内完成，合成器复用上一帧 → 用户感知卡顿。`Choreographer.FrameCallback` / `FrameMetrics`（API 24+）/ JankStats（Jetpack）可度量；线上建议采样式上报帧时长分布与掉帧会话。
- **度量指标**：掉帧率（掉帧数/总帧）、大掉帧（连续多帧）次数、帧时长分位、慢消息（主线程单条 > 预算的 Looper 消息）。区分「偶发掉帧（GC/IO/合成竞争）」与「持续掉帧（布局复杂/过度绘制）」。

### 2.2 合成层与特殊卡顿源

- **硬件加速合成**：常规 View 树内容进 GPU 合成；`TextureView`、部分动画（如过大的软件层）可能引入额外拷贝/回读，面试可提「合成层数量与带宽」是低端机卡顿源之一。
- **软件渲染路径**：关闭硬件加速或自定义 View 走 software canvas 时，主线程 CPU 绘制成本陡增——用层级与 trace 区分。
- **常见应用侧卡顿根因**：主线程 IO/锁/同步 binder；`onLayout` 链过深、嵌套权重；频繁 `requestLayout`；大列表未复用/未异步解码；动画中间层过多；锁竞争导致 RenderThread 等待。治理顺序：**先归因（trace+帧指标）再动手**。

### 2.3 手段清单

- 布局：扁平化、`ConstraintLayout`、避免 measure 两遍以上的自定义滥用、异步 inflate（谨慎与主线程视图树一致性）。
- 列表：ViewHolder 复用、差量刷新、图片异步解码（Performance 与 SystemDesign 图片库题联动）、`RecyclerView` 预取。
- 主线程纪律：卡顿监控（>700ms 消息）与 ANR 体系共享心跳方案。

#### 【面试官视角 · 流畅度】

- 加分：能画出 VSYNC→主线程→RenderThread→SF 链路；提到 JankStats/FrameMetrics 的采样与隐私；区分掉帧与 ANR 的量级。
- 减分：流畅度=布局优化背诵，无度量闭环。

#### 【追问链】

1. 如何定位"偶现掉帧"？→ 采样帧回调 + 生死簿对齐当时消息/网络/GC 事件。
2. 动画卡顿先查什么？→ 硬件层/动画对象是否在主线程被业务逻辑阻塞；是否有过度 invalidate。

## 三、包体积

### 3.1 度量先行

- 拆分口径：安装包下载体积 vs 安装后体积（`abi` 拆分、资源压缩后差异）；增量体积（每次 MR 对体积的影响）比绝对值更能驱动治理。
- 工具：AGP 的 size report、`bundletool` 按设备生成 APK 观察、R8 mapping、资源分析（未引用资源）、so 按 ABI/压缩比。

### 3.2 手段（按 ROI 排序讲）

1. **资源**：`shrinkResources` + 严格无引用删除；webp/avif 替代 png/jpeg；资源混淆与冗余清理；按语言/密度/ABI split。
2. **代码**：R8（优化+混淆+tree shaking）规则收敛——**规则文件是体积治理的政治问题**：每个 keep 都要 owner 与理由；移除无用反射路径/降级方案合并。
3. **so**：只保留目标 ABI（或使用 App Bundle 动态分发）；`strip` 调试符号；压缩方案与启动时解压成本权衡（`useLegacyPackaging`）；重逻辑下沉到按需下载/插件（注意合规与热修复边界，见 CrossSkill 第2页）。
4. **架构级**：特性模块动态下发（动态化交付）、资源云化、冗余 SDK 清理（一个功能三个 SDK 是常见肥胖源）。
5. **流程**：CI 体积门禁（MR 增量超阈值需评审）、体积看板到模块 owner。

#### 【面试官视角 · 包体积】

- 加分：谈「下载体积 vs 安装体积 vs 冷启动解压」三角 trade-off；提到 R8 规则治理与动态下发的合规成本。
- 减分：只背"用 webp、开混淆"，无门禁与 owner 机制，无法回答"如何防止反弹"。

#### 【追问链】

1. 动态下发的边界？→ 强依赖主流程的能力不能下发；下发失败要有本地兜底；政策与应用商店条款要审（见 CrossSkill）。
2. R8 规则越写越多怎么办？→ 规则评审 + 未使用规则扫描 + 反射点显式化（注册表代替隐式 keep）。
