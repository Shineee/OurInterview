# 第1页 · 架构演进：从单模块到多进程

面向架构师面试：架构题的答案永远是**在时间轴上的约束解**，没有"最正确"，只有"当前规模下代价最低"。本页讲演进路径与依赖治理，第2页讲多团队协作与技术债务。

## 一、演进路径：单模块 → 夌模块 → 多进程

### 问题

App 从 5 人维护到 300 人维护，架构要怎么演进？什么时候拆模块？什么时候拆进程？

### 机制级答案

**阶段0：单模块（快速验证期）**

- 形态：单 app module + 若干 package；接口即 package 可见性。
- 幸存条件：团队 ≤10 人、发版节奏统一、无并行大特性。此阶段的正确动作是**把领域边界用 package 先画出来**（`feature/`、`core/`、`data/` 雏形），为拆分留缝，而不是急着建 Gradle 模块。
- 拆分触发信号（不是人数焦虑，而是可观测信号）：编译时间超过交互忍受阈值、同一文件多人频繁冲突、无法按特性独立发版、测试无法按模块并行。

**阶段1：多模块（模块化）**

- 形态：`:app` + `:feature:xxx` + `:core:yyy`；依赖方向强制单向：`app → feature → core`，`feature` 之间禁止直接依赖。
- 通信：跨 feature 走 core 中的接口（SPI/路由，见 SystemDesign 组件化路由题）；数据模型放 core-api。
- 收益度量：模块级并行编译、按模块 owner 的 Review、特性可裁剪（App Bundle / 动态 feature 的前置）。
- 陷阱：过早拆出十几个"伪模块"（互相 implementation 依赖成环）；api/implementation 边界滥用导致隐藏依赖。

**阶段2：多进程**

- 触发条件（拆进程是稳定性与内存决策，不是模块化自然结果）：
  - 隔离：推送/音视频/WebView 等崩溃或内存大户不能拖垮主进程；
  - 内存：系统按进程算内存账，拆分可让部分组件按需拉起、用完即弃；
  - 后台存活：独立进程 + 前台服务策略（合规前提下）延长推送链路存活。
- 代价清单（面试必须主动讲）：Application 多次初始化（要做进程名分发的初始化清单）；跨进程通信成本与语义（Binder，见 SystemDesign IM 题）；数据不再共享内存（DB/SP 多进程模式或走 IPC）；调试与监控复杂度上升（生死簿要带进程维度）。
- 原则：**先模块化协议冻结，再多进程物理隔离**。进程边界一旦对外暴露 AIDL 就是长期 API 负债。

### 【为什么这样设计】

架构演进的底层约束是**组织规模与变更频率**（康威定律的工程侧）：拆分的粒度应与团队边界、发布节奏对齐；拆分过早增加协调成本，拆分过晚增加冲突与事故半径。进程隔离解决的是故障域与内存账，模块化解决的是变更域——用错药是架构事故高发区。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：是否理解拆分的"触发信号"而非教条；依赖方向治理；进程隔离的真实代价。
- 加分：给出量化触发线（如单模块编译 >3min、核心模块周冲突 >N 次）；主动讲多进程 Application 分发与多进程初始化清单。
- 减分："大厂都模块化所以我们也要拆 20 个模块"；把多进程当性能优化万能药。

### 【追问链】

1. 如何平滑迁移而不冻结需求？→ 绞杀者模式：新特性进新模块，旧代码按页迁移；接口先抽后搬，双跑校验。
2. 动态 feature 与多进程如何配合？→ 按需安装解决体积，进程隔离解决故障域，两者正交，不要混谈。

## 二、接口暴露与 SPI / 组件依赖治理

### 问题

模块化后，什么算"公共 API"？如何防止 core 变成大杂烩？

### 机制级答案

- **三级暴露模型**：
  1. `api`：跨模块契约（接口 + 数据类型），变更走评审与版本策略；
  2. `implementation`：模块内部实现，禁止外部 import（Gradle 边界 + 架构测试双重保证）；
  3. 运行时扩展点（SPI）：编译期无依赖的注册与发现（路由表 / ServiceLoader / 注解生成），用于"多实现、可插拔、避免反向依赖"。
- **SPI 使用纪律**：接口定义方拥有语义与兼容性责任；实现方注册需幂等；调用方必须处理「实现不存在」的降级。滥用 SPI 会把编译期问题推迟到运行时——**能编译期依赖的不要 SPI**，SPI 只解决"环依赖/可选实现/插件"三类真问题。
- **防腐层**：三方 SDK 与历史代码不得泄漏进 feature——统一包在 `core:infra` 或 feature 内部 adapter，替换 SDK 时改动面收敛。
- **依赖治理工具链**：模块依赖图 CI 检查（禁环、禁跨层）、`api/implementation` 规范 lint、依赖可视化报告。架构约束要**工具化**，靠 Review 记忆力的规范活不过三个版本。

### 【为什么这样设计】

模块化的核心资产是**依赖边界的可信度**：边界可信，团队才能并行；边界腐蚀（到处 implementation 泄漏、core 变垃圾桶），拆分收益归零而协调成本仍在。SPI 是边界的软扩展缝，滥用则缝变成新的耦合泥潭。

### 【面试官视角】

- 加分：能讲 api/implementation 与"公共 API 版本化"的联动；提到架构测试（依赖规则单测）。
- 减分：把 SPI 说成"就是个接口加注册"，不谈兼容与降级责任。

### 【追问链】

1. core 模块膨胀怎么办？→ 按稳定性分层：`core:api`（极稳）/`core:infra`（可换实现）/`feature:shared`（业务共享，控制增长）。
2. 接口兼容如何保证？→ 语义化版本 + 弃用期 + 调用方编译期失败优先于运行期行为变化。
