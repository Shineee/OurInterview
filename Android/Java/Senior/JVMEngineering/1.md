# 第1页 · GC 选型与内存泄漏排查

## 一、GC 基础：分代与三色

### 问题

为什么现代 JVM 默认分代？CMS/G1/ZGC 在回收集合上的根本差异是什么？

### 机制级答案

- **分代假说**：多数对象朝生夕灭（弱分代），存活对象倾向继续存活（强分代）。因此堆分新生代（Eden + S0/S1）与老年代：新生代用复制算法（存活少，复制成本低），老年代用标记-清除/整理。
- **可达性回收与三色标记**：从 GC Roots 出发，白（未访问）/灰（已访问未扫描完）/黑（已扫描完）。并发标记的难题是**标记期间对象引用在变**——CMS/G1 用写屏障 + 增量更新/原始快照（SATB）维护不丢对象；漏标会导致存活对象被回收（致命），所以屏障语义是并发 GC 正确性核心。
- **停顿模型差异**：
  - **CMS**（已废弃）：老年代并发标记-清除，目标低停顿，代价是碎片与浮动垃圾，需 Full GC 兜底整理；
  - **G1**：堆切成 Region，优先回收价值最高的 Region（停顿可设目标），整体趋向整理，有跨 Region 记忆集；
  - **ZGC/Shenandoah**（概念级）：着色指针/读屏障等手段把停顿做到亚毫秒量级，吞吐与内存占用有代价；版本可用性与生产成熟度以所用 JDK 为准，面试重在"读屏障 vs 写屏障、停顿与吞吐的坐标系"。

### 【为什么这样设计】

所有 GC 都是在**停顿、吞吐、内存、实现复杂度**四维空间里选点：没有全能冠军。选型叙事 = 业务对停顿的敏感度 + 堆大小 + JDK 版本能力。

### 【面试官视角】

- 加分：说清 CMS 被 G1 取代的历史原因（碎片、 Full GC 不可接受）；G1 停顿目标是尽力而为而非硬实时。
- 减分：背收集器名字不讲屏障与停顿来源。

## 二、GC 选型场景题

### 问题

三类服务请给 GC 方案并说明理由：① 在线交易 API（P99 敏感，堆 8G）；② 离线报表批处理（吞吐优先，堆 32G）；③ 超大堆低延迟网关（堆 64G+）。

### 机制级答案

- **① 在线 API（P99 敏感）**：中等堆 + 低延迟 → G1，设置合理 `-XX:MaxGCPauseMillis`（如 100-200ms 量级起步再压测调优）；观察点：Full GC 次数（应≈0）、暂停分位、Region 分配速率。JDK 较新版本可评估 ZGC，但要计入吞吐/占用实验数据再上——**选型话术必须带压测门槛**。
- **② 批处理（吞吐优先）**：并行收集器（Parallel/Throughput）即可，停顿不敏感，最大化单位时间处理量；避免为"技术先进"上低延迟 GC 换吞吐损失。
- **③ 超大堆网关**：G1 大堆已可用但停顿与标记周期压力上升；若 JDK 允许且团队有运维能力，ZGC 类低延迟收集器是方向。同时更工程的答案：**先问是否该拆服务把堆降下来**——架构解法优先于调 GC 参数。
- **容器环境**：务必开启容器感知（现代 JDK 默认更好），合理设 `-Xmx` 与 `MaxRAMPercentage`，避免宿主内存误判；容器 CPU 限额会影响并行度。
- **移动端对应**（Android 面试官追问时）：ART 以分代 + 并发为主，GC 类型（CC/CMC 等随版本演进）不可插拔选型，但同样有"避免分配风暴、软/弱引用语义、堆档位"问题——与 JVM 治理同思想不同旋钮。

#### 【面试官视角 · 选型】

- 加分：给"先定 SLA → 再选点 → 再压测验证 → 再定参数"流程；主动提 Full GC 是事故源。
- 减分：默认"最新最好"；无压测环节。

#### 【追问链】

1. 什么情况下必须调新生代比例？→ 分配速率高、Minor GC 后存活暴增（晋升失败）看 `age` 与晋升失败日志。
2. 如何判断堆大小设错了？→ 频繁 GC 且回收后占用仍高 = 堆小；占用长期很低且 GC 少 = 堆大可缩。

## 三、内存泄漏排查（堆转储分析路径）

### 问题

服务内存缓慢上涨直到容器被杀，如何排查？

### 机制级答案

- **取证时机**：
  - 先分层：RSS 上涨但 Java 堆稳定 → native/堆外/mmap（直接内存、Netty、JNI）；
  - 堆问题：`jmap -dump:live,format=b,file=...`（生产慎用 full dump 的停顿）或 `-XX:+HeapDumpOnOutOfMemoryError` + OOM 自动转储；更大堆用 JFR/NMT（Native Memory Tracking）与采样器（async-profiler alloc）先定位再 dump。
- **分析路径（MAT/VisualVM 思路）**：
  1. 总览：堆分代占比、各类实例数随时间对比（两次 dump diff）；
  2. **Dominator Tree**：按"支配的 retained 大小"排序，找异常大的集合/缓存；
  3. **Path to GC Roots（exclude weak/soft）**：从泄漏嫌疑对象向上找持有链——经典桶：静态集合、未取消的定时器/线程、监听器未反注册、ThreadLocal 未清理（线程池场景）、ClassLoader 持有整个应用（见第2页元空间）、序列化缓存。
  4. 验证：修改后灰度对比增长曲线——**泄漏修复的验收是斜率，不是单次水位**。
- **集合类误用**：无界 `HashMap` 撞哈希成链/树（Java 8 后成树，但仍无界）、`HashSet` 只加不删、`LinkedHashMap` 当 LRU 没设容量——治理是**所有缓存显式上限 + 过期策略**。

### 【为什么这样设计】

泄漏排查是把"随时间恶化的状态"还原为"某条引用链从未被切断"：dump 是快照考古，diff 是时间机器；GC Roots 语义让"谁该放手"可被机械定位——这套方法论与 Android LeakCanary（第1层工具自动，第2层人肉考古）完全同构。

### 【面试官视角：考察度 / 加分 / 减分】

- 考察点：RSS vs 堆的分层意识、dump 停顿风险、dominator/引用链方法。
- 加分：先采样后 dump 的生产节奏；ThreadLocal 与线程池组合泄漏；两次 dump diff 思路。
- 减分：OOM 才想到看内存；只看占用最大对象不做引用链；用 `System.gc` 当治疗手段。

### 【追问链】

1. 堆外涨了怎么查？→ NMT 开销注意、Netty direct memory 指标、`Cleaner` 泄漏、大 `MappedByteBuffer` 未 unmap（新版 API 改进情况以 JDK 文档为准）。
2. 如何做泄漏的线上兜底？→ 水位熔断 + 主动重启（优雅下线）止血，再治根因——止血与根治分两步讲。
