# 第1页 · 分布式常见题：ID、缓存、幂等与可靠投递

Android 应用同样面对分布式语义：多端 ID、本地/多级缓存一致性、请求重试幂等、推送与写操作可靠投递。本页给出机制级答案；每节按「问题 → 机制级答案 → 为什么这样设计 → 面试官视角 → 追问链」组织，尽量映射到客户端场景。

## 一、分布式 ID

### 问题

多机发号，如何设计全局唯一、趋势递增、可离线生成的 ID？

### 机制级答案

- **UUID（v1/v4）**：无中心、本地生成；缺点是 128 位、无序（v4 随机）导致 B+ 树二级索引页分裂写放大。v1 含时间与 MAC 概念但隐私与长度问题仍在。适合做外部可见的关联键，不适合做聚簇主键。
- **数据库号段（Leaf-segment 思路）**：DB 存 `max_id`，每次批量取一段（如 1000）本地递增，耗尽再取；双 buffer 预取平滑耗尽点。优点：趋势递增、依赖少；代价：DB 是发号点（可用多表/多行分片号段，如 Leaf-snowflake 的号段变体），要处理时钟与业务多维分片。
- **雪花（Snowflake）及其变体**：64 位 = 时间戳 + 机器位 + 序列号。趋势递增、无中心；三大坑：
  1. **时钟回拨**：NTP 回拨会发重复号——方案：等待回拨/拒绝发号/预留位与上次时间比对；
  2. **机器位分配**：静态配置简单但易冲突；需与部署平台协同或用 ZooKeeper/DB 租约；
  3. **序列溢出**：同一毫秒内自增到上限需自旋到下一毫秒。
- **选型话术**：库内主键优先号段/雪花（索引友好）；对外暴露 ID 优先雪花变体或有序雪花，并考虑**不暴露机器位语义**（安全）；极端多机高发号可分段服务化（号段服务集群）。

### 【为什么这样设计】

分布式 ID 的三角约束：唯一性（正确性）vs 有序性（存储性能）vs 可用性（去中心 vs 中心化精度）。几乎所有方案都是在这三点上做位与延迟的分配。

### 【面试官视角】

- 加分：主动讲时钟回拨与机器位治理；号段的双 buffer。
- 减分：只背雪花结构；说"UUID 一定不行"而无场景细分。

### 【追问链】

1. 只要唯一不要有序行不行？→ 行，接受索引与分页成本；分页深翻页在无序 ID 上更痛苦。
2. 跨机房如何分配机器位？→ 预留机房位/用租约中心；或统一发号服务，用延迟换运维简单。

## 二、缓存一致性

### 问题

DB 与缓存如何保持一致？先更新 DB 还是先删缓存？

### 机制级答案

- **结论先行（工程共识）**：经典 **Cache Aside**：读 miss → 查 DB → 回填缓存；写 → **先更新 DB，再（延迟）删除缓存**。原因是"先删缓存再更 DB"在并发读写下，旧值回填窗口更大；"先更 DB 再删缓存"仍有极小的并发不一致窗口（读请求在 DB 更新前读到旧值、在删缓存后回填——靠"短 TTL + 逻辑过期"兜底）。
- **删除失败怎么办**：删除不是事务的一部分——补救：
  1. **延迟双删**（更新前后各删一次 + 延迟间隔覆盖读回填）——窗口缩小但不为零；
  2. **订阅 binlog**（如 Canal 类组件订阅变更日志）异步删/刷缓存——业务与缓存解耦，可重放，工业主流；
  3. 缓存 TTL 兜底（一致性上限 = TTL）。
- **读写并发的细节**（追问高发）：脏回填的经典交错是"读线程查到旧 DB → 写线程更 DB 并删缓存 → 读线程用旧值回填"；缓解：回填时用版本号/CAS 判定、短 TTL、或延迟删除覆盖。
- **强一致场景**：不用缓存旁路删，改双写/变更订阅单写者，或接受短窗不一致但业务幂等——**面试要问清业务能容忍的不一致窗口**，一致性和成本一起谈。
- **更新缓存 vs 删除缓存**：更新缓存要业务算全量值且在高并发下做无谓计算；删除让下次读回填，更简单——除非计算极昂贵且读极频繁，才考虑写时更新。

### 【为什么这样设计】

缓存与 DB 不在同一事务域，分布式下没有免费的原子性：工程目标是**把不一致窗口压到业务可接受（通常毫秒~TTL）并保证最终收敛**。binlog 订阅的本质是"以 DB 为唯一事实源，缓存变成投影"——投影可以重建，系统就有自愈能力。

### 【面试官视角：考察点 / 加分 / 减分】

- 考察点：先更 DB 后删缓存的理由、删除失败补偿、binlog 方案、TTL 兜底意识。
- 加分：能画出脏回填交错时序；提到缓存击穿/穿透/雪崩与一致性是不同问题不要混答。
- 减分：坚持"先删缓存"且说不出并发窗口；声称能完全一致。

### 【追问链】

1. 热点 key 大量删击穿？→ 逻辑过期、互斥重建、异步刷新。
2. 多级缓存（本地+集中式）一致性？→ 本地缓存短 TTL + 广播失效（pub/sub）；接受更大窗口或按业务降级。

## 三、幂等与去重

### 问题

网络超时重试到处都是，如何保证"一次业务效果"？

### 机制级答案

- **定义分层**：网络层至少一次投递 ⇒ 业务层需要**效果恰好一次**（exactly-once effect）= 至少一次 + 幂等消费/去重。不要追求传输层 exactly-once（不存在免费方案）。
- **幂等设计模式**：
  1. **天然幂等**：置值类操作（`SET status=paid`）可重复；设计接口时优先置值而非增量；
  2. **唯一键去重表**：请求带 `biz_no`（业务单号）做唯一索引，插入成功才执行——去重与执行尽量同事务（本地消息表思路的兄弟）；
  3. **状态机**：订单状态只允许合法迁移，非法迁移直接返回当前状态（重复支付回调返回"已支付"）；
  4. **Token/预取号**：先发 token，消费时原子删 token + 执行，防表单重复提交；
  5. **分布式锁**：短临界互斥，**锁不是幂等本身**（锁释放后重试仍可能二次执行）——锁 + 去重键组合。
- **去重键选取**：客户端生成 `requestId`（一次交互一个）与业务键（多次交互同一效果一个）语义不同——支付场景业务键=订单+支付意图，不只是 HTTP requestId。
- **存储选择**：DB 唯一键（强、有成本）；Redis `SETNX`+TTL（快、可能丢，适合短窗防重）；布隆过滤器（只适合"大概率不存在"的前置拦截，有假阳性，不能当唯一真相）。

### 【为什么这样设计】

分布式系统的重试是常态不是异常：把"去重"做进业务事务边界，是用存储的原子性购买"效果唯一"的确定性；锁只能串行化，不能消除"两次都执行"的语义问题——这是面试分水岭。

### 【面试官视角】

- 加分：区分 requestId 与 biz_no；去重表与业务同事务；状态机返回语义（重复请求返回成功而非错误）。
- 减分："加锁就行"；用布隆过滤器当幂等终方案。

### 【追问链】

1. 去重表数据量？→ 按业务窗口滚动清理（保留期 ≥ 最大重试窗口 + 安全余量）。
2. 跨服务链路幂等？→ 每跳各自幂等 + 端到端携带业务键，不能只靠首跳去重。

## 四、消息可靠投递

### 问题

从生产到消费，消息如何做到不丢、不重、（按需）有序？

### 机制级答案

- **三段丢失面**：
  1. 生产 → Broker：网络失败/ Broker 拒绝；对策：同步发送确认（confirm/ack）、失败落重试表或本地消息表；
  2. Broker 持久化：多副本与刷盘策略（broker 配置）；面试重在"知道有持久化级别选项"；
  3. Broker → 消费者：拉取后处理中崩溃。对策：**手动 ack**（处理成功再提交位点）；"先 ack 后处理"必丢，"处理成功但没 ack"必重——所以**丢与重的权衡落在 ack 时机，重靠幂等消化**。
- **本地消息表（经典可靠模式）**：业务事务内写"待发消息"表 → 发送器轮询/事务性扫表发送 → 成功标记。把跨系统双写变为本地事务 + 重试扫表，不依赖 broker 的事务特性。
- **事务消息（概念级）**：broker 提供半消息（预备）+ 本地事务回查确认的协议（如 RocketMQ 类实现）——本质是本地消息表的协议化。
- **顺序**：全局有序代价高；实际用**分区有序**（业务 key 路由到同一队列）+ 单线程/单消费者处理该分区；乱序补救用版本号/状态机忽略旧消息。
- **消费端设计**：消费者水平扩展时并发处理同一分区会破坏顺序——用单线程拉取多线程投递（同一 key 走同一 worker）；毒消息（反复失败）进死信队列 + 告警人工介入，防止卡死位点。
- **端到端叙事模板**："生产确认 + 本地事务表保证**不丢**；消费手动 ack + 业务幂等保证**不重**；key 分区 + 约束并发保证**按需有序**；死信处理保证**故障不阻塞全局**。"

### 【为什么这样设计】

消息系统不承诺网络语义的完美：at-least-once 是务实基线，exactly-once effect 是业务侧用幂等拼出来的——把复杂度放在"可验证的业务键"上，比放在幻想的传输完美性上更可控。

### 【面试官视角：考察度 / 加分 / 减分】

- 考察点：三段丢失面、ack 时机、本地消息表、分区顺序、死信。
- 加分：主动区分"可靠投递"与"最终一致时间"（重试退避策略）；提到消费位点与业务库的原子性问题。
- 减分：只说"用 MQ 就不丢"；无幂等谈不重；死信=自动重试无限次。

### 【追问链】

1. 消费者与业务库如何原子？→ 本地消息表/事务消息，或至少去重键与业务同库事务。
2. 积压暴涨怎么办？→ 扩消费者（注意顺序 key）、扩分区、降下游慢操作、必要时临时降级非关键逻辑——先保链路再追数据。

> 全页收束：分布式四题共享一个内核——**承认网络不可靠，用"唯一事实源 + 去重/幂等 + 可重放"把正确性从时序巧合里解耦**。面试中能反复用这句话收拢细节，即是专家叙事。
